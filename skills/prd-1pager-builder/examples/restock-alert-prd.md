# PRD 예시 — 품절 사이즈 재입고 알림

2026-10-25 · 작성자

## 1. 요약

- **상황:** 옷장몰은 인기 상품의 일부 사이즈가 자주 품절된다. 품절 사이즈는 회색 버튼으로만 표시되고 별도 안내가 없다.
- **문제:** 고객은 재입고 시점을 알 수 없어 상품 페이지를 반복해서 확인하거나 구매를 포기한다.
- **해결 방안:** 품절 사이즈에 "재입고 알림 받기"를 제공한다. 재입고되면 앱 푸시로 알리고, 신청한 옵션이 선택된 구매 화면으로 바로 연결한다.
- **사용자 가치:** 품절 상품을 매일 확인하지 않아도 재입고 소식을 바로 받고, 알림에서 한 번에 구매할 수 있다.
- **비즈니스 효과:** 품절 이탈 고객 재유입, 재입고 관련 CS 문의 감소
- **이번 버전 범위:** 알림 신청, 재입고 감지와 앱 푸시 발송, 구매 화면 바로 연결, 내 알림 목록

## 2. 배경

- **시즌 상황:** 가을·겨울 아우터는 인기 사이즈가 빨리 품절된다. 시즌이 끝나기 전에 재입고 수요를 잡아야 한다. (가정)

**벤치마킹**

재입고 알림을 제공하는 쇼핑몰 제작 도구와 마케팅 도구를 비교해 기획에 참고할 점을 정리한다.

| 대상 | 발송 방식 | 특징 | 반영할 점 |
|---|---|---|---|
| 식스샵 재입고 알림 (국내 쇼핑몰 제작 도구) | 관리자가 원하는 시점에 직접 발송 | 상품 옵션 단위로 신청을 받고, 신청 고객 중 일부만 골라 발송할 수 있음 | 일부 고객 선택 발송 방식은 순차 발송 재검토 시 참고 (18장 결정 1) |
| Braze 재입고 알림 (마케팅 자동화 도구) | 재고 변경 시 자동 발송 | 수신 동의한 사용자에게만 발송. 10분 단위로 발송 인원을 제한하며 분당 최대 1만 명. 가격 인하 알림과 같은 구조로 운영 | 발송 속도 제한은 16장 동시 발송 부하 대응에 참고. 가격 인하 알림(12장 제외 범위)은 다음 버전에서 같은 구조로 확장 가능 |
| WooCommerce 재입고 알림 플러그인 (해외 쇼핑몰 플랫폼, 가이드 글 기준) | 재고 상태 변경 즉시 자동 발송 | 이메일, SMS, 푸시 지원. 재입고 이벤트·고객별로 알림을 1회만 보내도록 설정 권장 | 원칙 2(신청 1건당 알림 1회)와 같은 방향 |
| 국내 패션 플랫폼 (무신사, 29CM, 지그재그 등) | 확인 필요 | 확인 필요 | 앱에서 직접 확인 후 추가 |

## 3. 주요 사용자

**이 사용자의 불편을 먼저 해결하는 이유:** 품절 사이즈를 기다리는 고객은 이미 이 상품을 사기로 마음먹은 상태다. 구매 직전 단계에서 이탈하므로, 재입고 시점에 다시 연결하면 구매로 이어질 가능성이 높다. (가정, 18장 확인 사항 4)

| 구분 | 누구 | 기대하는 점 |
|---|---|---|
| 주 사용자 | 옷장몰 앱 회원 중 원하는 사이즈가 품절된 고객 | 매일 확인하지 않고 재입고 소식을 받기 |
| 부 사용자 | 같은 브랜드를 자주 사는 단골 고객 (가정) | 인기 상품을 놓치지 않기 |
| 내부 사용자 | MD, CS 담당 | 대기 수요 파악, 반복 문의 감소 |
| 기기 | 앱 (iOS·Android) | 웹은 이번 버전에서 제외 (18장 확인 사항 3) |

## 4. 문제

**문제 정의:** 고객은 원하는 사이즈가 품절되면 언제 다시 들어오는지 알 방법이 없어, 상품 페이지를 반복해서 확인하거나 구매를 포기한다.

**근거 (예시, 실제 문서라면 출처 필수)**

| 근거 | 내용 |
|---|---|
| CS 문의 | 최근 3개월 1:1 문의 중 "재입고 언제 되나요"가 상위 3위 (가정) |
| 행동 로그 | 상품 상세에서 품절 사이즈를 누른 뒤 그대로 나간 비율이 높음 (가정, 로그 분석 필요) |
| 고객 인터뷰 | 아직 진행 전. 5명 인터뷰로 확인 예정 (18장) |

## 5. 문제 원인 분석

핵심 원인은 재입고 정보를 고객에게 전달하는 경로가 없다는 점이다.

| 번호 | 원인 | 설명 | 이번 버전 대응 |
|---|---|---|---|
| 원인 1 | 재입고 정보 전달 경로 없음 | 품절 화면에 재입고 여부나 알림 신청 수단이 없어 고객이 직접 확인해야 한다. (현재 화면 기준) | 해결 (REQ-01~04) |
| 원인 2 | 확인 비용이 큼 | 재입고 시점이 불규칙해 고객이 여러 번 방문해야 한다. (가정) | 해결 (REQ-04) |
| 원인 3 | 재입고 후 빠른 재품절 | 늦게 알면 재입고돼도 구매하지 못한다. (가정, 재입고~재품절 시간 로그 분석 필요) | 해결 (REQ-04·05) |
| 원인 4 | 재입고 물량 부족 | 수요 대비 발주량이 적어 금방 다시 품절된다. (가정) | 제외 (MD 영역, 다음 버전에서 REQ-08로 수요 데이터 제공) |

## 6. 가설

**가설:** 품절 사이즈에 재입고 알림을 제공하면, 품절로 이탈하던 고객 중 일부가 재입고 시점에 돌아와 구매할 것이다.

| 항목 | 내용 |
|---|---|
| 근거 | 고객이 재입고 사실을 모르거나 늦게 알아서 구매를 놓친다 (5장 원인 1~3) |
| 검증 방법 | 베타 기간의 재입고 알림 구매 전환율 (15장) |
| 맞다고 판단하는 기준 | 15장 핵심 지표가 목표치에 도달 |
| 틀렸다고 판단하는 기준 | 알림 열람률은 높은데 구매 전환이 거의 없으면, 알림이 아니라 재고 물량이 문제라고 본다 (5장 원인 4) |

## 7. 목표

1. **품절 이탈 고객 재유입.** 재입고 알림을 통해 구매 전환을 확보한다.
2. **재입고 관련 CS 문의 감소.** 고객이 문의하지 않아도 재입고 여부를 알 수 있게 한다.
3. **MD의 재입고 수요 파악 지원.** 상품별 알림 신청 수를 발주 판단에 활용한다. (다음 버전)

## 8. 핵심 사용자 여정

해결 방안과 별개로, 품절 사이즈를 만난 고객이 거치는 단계와 단계별 니즈를 정리한다.

| 단계 | 고객 행동 | 고객 니즈 | 현재 불편 |
|---|---|---|---|
| 1. 품절 확인 | 원하는 사이즈를 골랐는데 품절 표시를 본다 | 다시 들어오는지 알고 싶다 | 재입고 여부를 알 수 없다 |
| 2. 대기 | 다른 쇼핑몰을 찾거나, 며칠 뒤 다시 확인한다 | 계속 확인하지 않고 기다리고 싶다 | 직접 반복해서 확인해야 한다 |
| 3. 재입고 | 재입고 사실을 알게 된다 | 들어오자마자 알고 싶다 | 늦게 알거나 모르고 지나간다 |
| 4. 구매 | 상품을 다시 찾아 사이즈를 고르고 결제한다 | 빠르게 구매하고 싶다 | 상품을 다시 찾아야 하고, 그사이 재품절될 수 있다 |

이번 기능은 2~4단계의 불편을 해결한다. 2단계는 알림 신청, 3단계는 푸시 발송, 4단계는 구매 화면 바로 연결로 대응한다 (9장).

## 9. 해결 방안

| 방법 | 판단 | 이유 | 재검토 시점 |
|---|---|---|---|
| 재입고 알림 신청 (앱 푸시) | 채택 | 원인 1~3을 직접 해결하고 발송 비용이 없음 | 해당 없음 |
| 재입고 예정일 안내 | 제외 | 입고 일정이 자주 바뀌어 틀린 약속이 될 위험 | 입고 데이터 정확도 확인 후 |
| 품절 시 비슷한 상품 추천 | 제외 | 원하는 상품을 사려는 고객의 문제를 해결하지 못함. 별도 PRD로 작성 | 다음 분기 |
| 문자·카카오 알림톡 발송 | 보류 | 발송 비용과 채널 검수 필요. 앱 푸시 효과 확인 후 검토 | 출시 4주 리뷰 |

## 10. 기능 요구사항

**공통 원칙** (기획·개발 중 판단이 필요할 때 따르는 기준)

| 번호 | 원칙 |
|---|---|
| 원칙 1 | 재고가 판매 가능 상태로 반영된 뒤에만 발송한다. |
| 원칙 2 | 신청 1건당 알림은 1회만 발송하고, 발송 후 신청을 자동 종료한다. |
| 원칙 3 | 재입고 일정을 안내하지 않는다. "곧 들어와요" 같은 문구도 사용하지 않는다. |
| 원칙 4 | 알림이 구매를 보장하지 않는다는 점을 문구에 명시한다. 예) "재고가 빨리 소진될 수 있어요" |
| 원칙 5 | 야간 발송 기준은 법무 확인 후 정한다. 정보통신망법상 광고성 정보에 해당하는지 확인 필요 (18장 확인 사항 1) |

**기능 목록**

· **필수:** 없으면 출시 불가

· **출시 직후:** 출시 후 1~2주 안

· **다음 버전:** 이번 범위 아님.

<span style="color:gray">*\*REQ: 요구사항(Requirement) 번호. 디자인 요청서·개발 요청서에서도 같은 번호로 연결한다.*</span>

| 번호 | 기능 | 완료 조건 (이렇게 되면 완료) | 우선순위 |

| REQ-03 | 알림 권한 안내 | 앱 푸시가 꺼진 고객도 신청은 저장된다. 이때 "알림을 켜야 받을 수 있어요"와 설정 이동 버튼이 보인다. | 필수 |
| REQ-04 | 재입고 감지·발송 | 옵션 재고가 0에서 1 이상이 되면 일정 시간 안에 신청자 전원에게 푸시가 나간다. 시간 기준은 개발과 협의 (18장 확인 사항 2) | 필수 |
| REQ-05 | 구매 화면 바로 연결 | 푸시를 누르면 해당 상품 상세가 열리고, 신청한 옵션이 선택된 상태다. | 필수 |
| REQ-06 | 내 재입고 알림 목록 | 마이페이지에서 신청 내역(상품, 옵션, 신청일, 진행 여부)을 보고 해제할 수 있다. | 출시 직후 |
| REQ-07 | 신청 자동 종료 | 알림 발송 후, 또는 상품이 판매 종료되면 신청이 끝나고 목록에 "종료"로 표시된다. | 필수 |
| REQ-08 | 대기 인원 조회 (내부) | MD가 관리자 화면에서 상품·옵션별 신청자 수를 볼 수 있다. | 다음 버전 |

## 13. 예외·실패 처리

| 상황 | 처리 방식 |
|---|---|
| 신청자 수가 재입고 수량보다 많음 | 전원에게 발송하고 선착순 구매. 발송 속도를 제한해 나눠 보냄 (원칙 4, 18장 결정 1) |
| 알림 확인 시점에 재품절 | 상세 화면에 "방금 품절됐어요. 다시 알림 받을까요?"와 재신청 버튼 |
| 앱 푸시 권한이 꺼져 있음 | 푸시 미발송, 앱 내 알림함에만 저장 |
| 상품 판매 종료 | 신청 자동 종료. 알림함에 "판매가 종료됐어요" |
| 재고가 0 → 1 → 0 → 1로 짧게 반복 (반품 입고 등) | 같은 신청에는 알림 1회만 발송 (원칙 2) |
| 발송 중 서버 오류 | 자동 재시도 후 실패 시 로그 기록, 담당자 확인 (개발 협의 필요) |
| 회원 탈퇴 | 신청 내역 삭제 |

## 14. 필요한 데이터

| 데이터 | 출처 | 용도 |
|---|---|---|
| 옵션별 재고 수량 | 기존 재고 시스템 | 재입고 감지 (REQ-04) |
| 판매 상태 (판매 중 / 품절 / 판매 종료) | 기존 상품 관리 시스템 | 신청 자동 종료 (REQ-07) |
| 알림 신청 내역: 회원, 상품, 옵션, 신청 시각, 상태 | 신규 생성 | 발송 대상, 내 알림 목록 |
| 푸시 토큰, 알림 수신 동의 여부 | 기존 회원 시스템 | 발송 가능 여부 판단 |
| 행동 기록 (신청, 발송, 열람, 구매) | 분석 도구 | 성공 지표 (15장) |

## 15. 성공 지표

목표치는 베타 2주 데이터로 기준선을 잡은 뒤 정한다. 7일·4주 측정 기간은 분석가와 확정한다.

| 구분 | 지표 | 계산 방법 | 확인 목적 |
|---|---|---|---|
| 핵심 | 재입고 알림 구매 전환율 | 알림 받고 7일 안에 그 옵션을 산 고객 ÷ 알림 받은 고객 | 목표 1 달성 여부 |
| 퍼널 | 신청률 | 알림 신청 수 ÷ 품절 옵션을 누른 수 | 버튼 위치·문구의 적절성 |
| 퍼널 | 알림 열람률 | 푸시를 누른 수 ÷ 보낸 푸시 수 | 알림 문구·발송 시점의 적절성 |
| 퍼널 | 열람 후 구매율 | 구매 수 ÷ 푸시를 누른 수 | 재고 소진, 가격 등 구매 저해 요인 |
| 보조 | 재입고 문의 수 | 출시 전 4주 vs 출시 후 4주 CS 문의 수 | 목표 2 |
| 가드레일 | 앱 알림 수신 거부율 | 알림을 끈 고객 수, 출시 전후 비교 | 알림 피로 증가 여부 |
| 보조 | 알림 확인 후 재품절률 | 푸시를 눌렀을 때 이미 품절인 수 ÷ 푸시를 누른 수 | 순차 발송 전환 판단 (18장 결정 1) |

| 리스크 | 내용 | 대응 |
