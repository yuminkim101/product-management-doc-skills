# PRD·원페이저 빌더

기획 내용을 원페이저와 PRD로 정리한다. 내용을 그럴듯하게 채우는 게 목적이 아니다. 같은 틀로 쓰고, 모르는 것은 모른다고 표시하고, 두 문서가 다른 말을 하지 않게 하는 것이 목적이다.

- **원페이저**: 의사결정자가 3분 안에 읽고 방향에 답을 주는 문서
- **PRD**: 방향이 정해진 뒤 디자인·개발이 참고하는 상세 문서

## 파일

| 경로 | 용도 |
|---|---|
| `templates/one-pager.md` | 원페이저 양식, PRD 장 대응표 |
| `templates/prd.md` | PRD 양식과 장별 작성법 |
| `review-checklists/one-pager-checklist.md` | 원페이저 점검 |
| `review-checklists/prd-checklist.md` | PRD 점검 |
| `examples/` | 채우는 방식 참고용. 내용은 옮겨 쓰지 않는다. 견본과 양식의 표 구성이 다르면 양식을 따른다 |

## 순서 판단

| 요청 | 작업 |
|---|---|
| 원페이저 요청, 또는 메모만 있음 | 원페이저 작성 |
| 원페이저를 주며 PRD 요청 | 원페이저 → PRD 확장 |
| PRD 요청, 원페이저 없음 | PRD 작성 후 원페이저도 함께 |
| PRD를 주며 원페이저 요청 | PRD → 원페이저 요약 |
| 점검·검토 요청 | 점검 |
| 내용 변경 | 수정 |

"기획서 써줘"처럼 애매하면 원페이저부터 쓰고, 피드백 후 PRD로 확장할 수 있다고 한 줄 안내한다. 방향이 바뀌면 긴 문서일수록 다시 쓸 양이 많다.

## 공통 작성 순서

1. 입력에서 정해진 사실(문제, 대상, 해결 방향, 범위, 일정)만 뽑는다.
2. 서비스·기능, 누가 겪는 문제, 만들려는 것 세 가지가 모두 없을 때만 한 번에 묶어 묻는다. 하나라도 있으면 묻지 않고 쓴다.
3. 양식대로 쓴다.
4. 점검표로 점검하고, 걸린 항목은 고치거나 확인 필요 사항으로 옮긴다.
5. 채팅에는 결과 요약과 먼저 정할 확인 사항 3~4건만 적는다.

## 순서별 규칙

**원페이저 작성**: 상세 문서는 "작성 전". 피드백 요청 사항에 답할 수 있는 질문 2~3개를 넣는다.

**원페이저 → PRD 확장**: 대응표대로 이어받는다. 자세히 풀어 쓰는 건 괜찮지만 결론(문제, 가설, 지표, 범위)은 바꾸지 않는다. 피드백 중 결정된 것은 18장 결정 사항, 남은 것은 확인 필요 사항으로 옮긴다. 피드백으로 결론이 바뀌었으면 원페이저도 고칠지 묻는다. PRD 19장에 원페이저를 넣고, 원페이저의 상세 문서 링크를 PRD로 바꾼다.

**PRD 작성**: 장 순서와 번호를 바꾸지 않는다. 끝나면 원페이저를 별도 파일로 함께 만든다. 사용자가 PRD만 원하면 생략한다.

**PRD → 원페이저 요약**: PRD 문구를 줄여 옮긴다. PRD에 없는 내용은 더하지 않는다.

**점검**: 항목별 통과 / 보완 필요를 표로 보여 주고 수정 문안을 붙인다. 두 문서가 다 있으면 불일치도 본다. 요청 전에는 문서를 고치지 않는다.

**수정**: 바뀐 부분만 고치고 버전·수정일·변경 이력을 올린다. 다른 문서에도 반영할지 묻는다. 요구사항이 바뀌면 handoff-doc-builder로 요청서 동기화가 필요하다고 알린다.

## REQ 규칙

- PRD 10장 요구사항은 `REQ-01`처럼 두 자리. 원본에 다른 번호 체계가 있으면 바꿀지 묻고, 답이 없으면 REQ로 쓴다.
- 기능 목록 표 바로 위에 회색 주석을 둔다. 문구는 고정한다.
  - 문구: `*REQ: 요구사항(Requirement) 번호. 디자인 요청서·개발 요청서에서도 같은 번호로 연결한다.`
  - Markdown: `<span style="color:gray">` 로 감싸고 기울임
  - Claude 문서: 글자 색을 지정할 수 없어 기울임만
  - 완료 조건 주석이 있으면 그 다음 줄에 둔다
- 다른 장에서도 같은 번호로 가리킨다. 예: "해결 (REQ-01~04)"
- 삭제된 번호는 다시 쓰지 않는다. 나뉘면 `REQ-04a`, `REQ-04b`
- 원페이저에는 쓰지 않는다

## 내용 원칙

- 확인되지 않은 주장 뒤에는 `(가정)`. 확인 방법과 담당을 확인 필요 사항에 적는다.
- 수치·날짜·출처를 지어내지 않는다. 모르면 "미정", 예시가 꼭 필요하면 "(예시)".
- 같은 내용을 여러 장에 반복하지 않고 "(18장 확인 사항 2)"처럼 가리킨다.
- 영문 코드는 REQ와 화면 ID(예: PD-01)만 쓴다. 원칙·원인·확인 사항은 "원칙 1"처럼 우리말 번호.

## 문체

실무 기획자가 직접 쓴 문서처럼 쓴다.

- "~한다"체 평서문 또는 개조식. 한 문장에 한 내용.
- 쓰지 않는 표현
  - 뜻 없는 꾸밈말: 다양한, 효과적으로, 원활한, 혁신적인, 최적의, 핵심적인 역할, 극대화
  - 번역투: ~를 통해, ~를 가능하게 한다, ~에 있어서, ~하는 것이 중요하다
  - 비유: 한 축, 뼈대, 큰 그림, 청사진, 나침반, 퍼즐 조각. "관문 조건" → "단계별 기준", "범위 밖" → "제외 범위"처럼 실제로 가리키는 말로 바꾼다
  - 문서를 소개하는 문장: "이 문서는 ~를 다룬다", "아래와 같이 정리했다"
- 굵은 글씨는 항목 이름에만 쓰고 문장 강조에는 쓰지 않는다.
- 줄표(—)는 제목 외에는 쓰지 않는다.

## 출력

- 원페이저와 PRD는 항상 별도 문서.
- 기본은 Claude 문서. 새로 만들기 전에 승인을 받고, 승인 전에는 Markdown 파일로 보여 준다. 이미 있는 Claude 문서는 직접 고친다.
- Notion, Confluence, Google Docs 등 외부에 새로 만드는 것은 사용자가 요청하고 최종 승인한 경우에만.
