# 핸드오프 문서 빌더

PO·기획자가 쓴 기획서를 디자이너와 개발자가 바로 작업에 들어갈 수 있는 문서로 바꾸고, 원본이 바뀌었을 때 문서들을 같은 기준으로 맞춰 주는 스킬입니다. "핸드오프"는 기획 단계의 결과물을 다음 담당자(디자인·개발)에게 인계한다는 뜻입니다.

이 스킬이 해결하려는 문제는 세 가지입니다.
- 기획서에는 디자인·개발에 필요한 정보(상태별 화면, 예외 처리, 문구, 데이터, 완료 기준)가 흩어져 있거나 빠져 있다.
- 기획서가 수정돼도 디자인·개발 문서에 반영이 늦거나 누락된다.
- 요청자마다 요청서 형식과 품질이 다르다.

## 폴더 구성

| 경로 | 언제 읽는가 |
|---|---|
| `request-prompts/request-types.md` | 작업 시작 시. 문서 종류와 작업 유형을 고르고 필요한 입력을 확인 |
| `templates/design-request.md` | 디자인 요청서를 쓰거나 고칠 때 |
| `templates/dev-request.md` | 개발 요청서를 쓰거나 고칠 때 |
| `templates/traceability-table.md` | 요구사항 번호 규칙, 매핑표, 변경 이력이 필요할 때 |
| `review-checklists/design-request-checklist.md` | 디자인 요청서 작성 직후 |
| `review-checklists/dev-request-checklist.md` | 개발 요청서 작성 직후 |
| `review-checklists/sync-checklist.md` | 동기화(원본 변경 반영) 후 |

## 작업 흐름

### 0-1. 문서 종류 판단
요청 문장을 보고 어떤 문서를 만들지 고릅니다.

| 요청 표현 | 문서 |
|---|---|
| 디자인 요청서, 디자이너한테 넘길, 화면 설계 요청 | 디자인 요청서 |
| 개발 요청서, 개발자한테 넘길, 개발 스펙, Jira 티켓 | 개발 요청서 |
| 둘 다, 핸드오프 문서 세트 | 두 문서 모두 (같은 요구사항 번호 사용) |
| "이 기획서 정리해줘"처럼 애매함 | 한 줄로 어느 쪽인지 확인 |

이미 한쪽 문서가 있는 상태에서 다른 쪽을 요청하면, 기존 문서의 요구사항 번호와 "확인할 것"을 그대로 이어받습니다. 같은 요구사항이 두 문서에서 다른 번호를 가지면 동기화가 깨지기 때문입니다.

### 0-2. 작업 유형 판단
- **A. 신규 작성**: 원본만 있고 요청서가 없음
- **B. 동기화**: 기존 요청서 + 수정된 원본이 있음
- **C. 점검만**: 이미 쓴 요청서를 검토
- **D. 피드백 반영**: 디자인 시안 피드백이나 QA 이슈를 수정 요청으로 정리

각 유형의 입력 조건은 `request-prompts/request-types.md`에 있습니다.

### A. 신규 작성
1. **원본 읽기**: 목적, 대상 사용자, 기능 요구사항, 정책, 일정, 참고 자료를 뽑습니다.
2. **요구사항 번호 확인·부여**: 원본에 번호(REQ, FR, 이슈 번호 등)가 있으면 그대로 씁니다. 없으면 `REQ-01`부터 붙이고, 원본에도 같은 번호를 적어 두라고 안내합니다. 이 번호가 디자인·개발 문서와 이후 동기화를 잇는 기준입니다.
3. **문서별 재구성**
   - 디자인 요청서: 요구사항을 디자이너가 그릴 **화면** 단위로 묶습니다.
   - 개발 요청서: 요구사항을 개발자가 구현할 **기능** 단위로 묶고, 기능마다 동작 규칙·데이터·예외·완료 기준을 정리합니다.
4. **빈 곳 찾기**: 원본에 근거가 없는 상태, 정책, 수치, 문구는 지어내지 말고 "확인할 것"으로 올립니다.
5. **양식에 맞춰 작성**: 해당 템플릿 구조를 따릅니다.
6. **점검**: 해당 점검표로 점검하고, 걸린 항목은 "확인할 것" 표에 질문으로 남깁니다.
7. **출력**: 아래 "출력 형식"을 따릅니다.

요청서 본문은 사람이 읽는 부분이라 관리용 번호를 최소한으로 씁니다. 디자인 요청서 본문에는 번호를 쓰지 않고 화면을 ①②로 부릅니다. 개발 요청서는 개발자가 티켓과 대조해야 하므로 기능 제목 옆에만 요구사항 번호를 붙입니다. 전체 매핑은 맨 아래 접힌 "관리 정보"에 둡니다.

### B. 동기화 (원본 변경 반영)
1. 기존 요청서(디자인·개발 중 있는 것 전부)와 수정된 원본을 받습니다. 없으면 요청합니다.
2. **번호 단위 비교**: 요구사항마다 `추가 / 변경 / 삭제 / 동일`을 판정합니다. 번호 없이 새로 생긴 요구사항은 다음 번호를 부여합니다.
3. **영향 범위 정리**: 바뀐 요구사항이 연결된 화면(디자인)과 기능(개발)을 찾습니다.
4. **문서 갱신**: 영향받는 부분만 고칩니다. 변경 없는 부분은 문장도 건드리지 않습니다. 이미 작업이 진행된 부분까지 흔들리면 안 되기 때문입니다.
5. **변경 이력 기록**: 문서마다 버전을 올리고 변경 이력을 적습니다.
6. **전달용 변경 요약**: 디자이너용, 개발자용을 각각 3~5줄로 씁니다. 받는 사람이 다시 봐야 할 범위가 다르기 때문입니다.
7. **점검**: `review-checklists/sync-checklist.md`로 점검합니다.

### C. 점검만
해당 점검표 기준으로 항목별 통과/보완 필요를 표로 정리하고, 보완이 필요한 항목은 수정 문안을 제안합니다.

### D. 피드백 반영
피드백을 요구사항 번호 기준으로 분류하고, 각 건을 "현재 → 요청 사항 → 근거"로 정리합니다. 원본 정책과 충돌하는 피드백은 반영하지 말고 "충돌 - PO 판단 필요"로 표시합니다.

## 작성 원칙

- **원본에 없는 정책·수치·문구는 만들지 않습니다.** 필요한데 없으면 "확인할 것"으로 올리고 누구에게 확인할지(PO, 개발, 디자인, 법무 등)를 적습니다. 요청서가 추측을 사실처럼 담으면 잘못된 화면이나 기능이 그대로 만들어지기 때문입니다.
- **개발 요청서에서 구현 방법은 정하지 않습니다.** 데이터베이스 구조, API 설계, 기술 선택은 개발자가 정할 영역입니다. 요청서는 "무엇이 어떻게 동작해야 하는가"까지만 씁니다.
- **받는 사람 관점으로 씁니다.** 배경은 짧게, 작업에 필요한 내용은 구체적으로 씁니다.
- **용어 통일**: 같은 대상은 같은 단어로 부르고, 원본 용어를 우선합니다. 디자인·개발 문서 사이에서도 용어를 맞춥니다.

## 문체

실무 기획자가 직접 쓴 문서처럼 씁니다.

- 개조식 또는 "~한다"체 평서문. 한 문장에 한 내용.
- 쓰지 않는 표현
  - 뜻 없는 꾸밈말: 다양한, 효과적으로, 원활한, 혁신적인, 최적의, 핵심적인 역할, 극대화
  - 번역투: ~를 통해, ~를 가능하게 한다, ~에 있어서, ~하는 것이 중요하다
  - 비유: 한 축, 뼈대, 큰 그림, 청사진, 나침반, 퍼즐 조각. 실제로 가리키는 말로 바꾼다 (예: "범위 밖" → "이번에 하지 않는 것")
  - 문서를 소개하는 문장: "이 문서는 ~를 다룬다", "아래와 같이 정리했다"
- 굵은 글씨는 항목 이름에만 쓰고 문장 강조에는 쓰지 않습니다.
- 줄표(—)는 제목 외에는 쓰지 않습니다.

## 출력 형식

- 기본값은 **Claude 문서(Docs)** 입니다. 다만 새 문서를 만들기 전에 사용자 승인을 받고, 승인 전에는 Markdown 파일로 보여 줍니다.
- 외부 도구(Notion, Confluence, Jira 등)에 페이지나 티켓을 만드는 것은 사용자가 명시적으로 요청하고 최종 승인한 경우에만 합니다. Jira 티켓 요청이 오면 먼저 티켓 목록(제목·설명·완료 기준)을 보여 주고 승인을 받습니다.
- 두 문서를 함께 만들면 각각 별도 파일로 만들고, 채팅에는 두 문서 공통의 "확인할 것" 중 우선순위 높은 3~4건만 짧게 보여 줍니다.
