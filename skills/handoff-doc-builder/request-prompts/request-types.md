# 요청 유형별 프롬프트

요청 유형마다 필요한 입력과 진행 순서를 고정해 둔 문서입니다. 사용자가 아래 형식을 그대로 쓰지 않아도, 빠진 입력이 있으면 이 기준으로 되물어 채웁니다. 단, 질문은 꼭 필요한 것만 한 번에 묶어서 합니다.

입력이 메모 수준으로 짧아도 작성을 멈추지 않습니다. 정해진 것만으로 문서를 만들고, 빈 곳은 "확인할 것"으로 돌려줍니다. 사용자가 그 질문 목록을 보고 결정하는 것이 더 빠르기 때문입니다.

1~5는 디자인 요청서, 6~7은 개발 요청서, 8은 두 문서 공통입니다.

---

## 1. 신규 화면 디자인 요청 (모드 A)

**필수 입력**
- 원본 문서(PRD·기획서) 전문 또는 링크
- 요청 범위: 전체 기능 / 특정 화면만

**있으면 좋은 입력**
- 디자인 마감 희망일
- 플랫폼(앱 iOS·Android / 웹 / 반응형)
- 참고 레퍼런스(경쟁사 화면, 기존 디자인 시스템 컴포넌트)

**사용자용 예시 프롬프트**
```
[신규 디자인 요청]
원본: (PRD 붙여넣기 또는 링크)
범위: 장바구니 쿠폰 적용 기능 전체
플랫폼: 앱(iOS/Android)
마감: 11/14
참고: 기존 쿠폰함 화면 컴포넌트 재사용 희망
```

---

## 2. 기존 화면 수정 요청 (모드 A 변형)

**필수 입력**
- 수정 대상 화면(이름 또는 SCR ID, 가능하면 현재 화면 캡처나 Figma 링크)
- 수정 이유(정책 변경, 지표 개선, 사용자 불만 등)와 근거 문서

**작성 시 주의**
- "현재 → 변경 후"를 항목별로 나란히 씁니다.
- 수정 범위 밖 요소는 "변경 없음"으로 명시해 디자이너가 손대지 않도록 합니다.

**사용자용 예시 프롬프트**
```
[화면 수정 요청]
대상: 주문서 화면 결제수단 영역
이유: 간편결제 노출 순서 변경 (정책서 v2.3)
근거: (정책서 붙여넣기)
```

---

## 3. 원본 변경 동기화 (모드 B)

**필수 입력**
- 기존 디자인 요청서(최신 버전)
- 수정된 원본 문서

**있으면 좋은 입력**
- 이전 원본 문서(비교 정확도가 올라감)
- 디자인 진행 상황(어느 화면까지 작업됐는지)

**사용자용 예시 프롬프트**
```
[요청서 동기화]
기존 요청서: (v1.0 붙여넣기)
수정된 PRD: (붙여넣기)
디자인 진행: SCR-01~03 시안 완료, SCR-04 작업 중
```

**진행 상황을 받았다면**: 이미 시안이 완료된 화면에 영향이 있는 변경은 변경 요약 맨 위에 "재작업 필요"로 따로 표시합니다.

---

## 4. 요청서 점검 (모드 C)

**필수 입력**
- 점검할 디자인 요청서
- 가능하면 원본 문서(원본 대조 점검이 가능해짐)

원본 없이 요청서만 받으면, 원본 대조 항목은 "원본 미제공으로 점검 불가"로 표시합니다.

---

## 5. QA·디자인 피드백 반영 (모드 D)

**필수 입력**
- 피드백 내용(리뷰 코멘트, QA 이슈 목록 등)
- 해당 디자인 요청서

**작성 시 주의**
- 피드백마다 출처(누가, 어디서)를 남깁니다.
- 정책·요구사항과 충돌하는 피드백은 반영 대신 "충돌 - PO 판단 필요"로 표시합니다.

---

## 6. 신규 개발 요청 (개발 요청서, 모드 A)

**필수 입력**
- 원본 문서(기획서·메모) 또는 이미 만든 디자인 요청서

**있으면 좋은 입력**
- 디자인 시안 링크
- 대상 플랫폼(앱 / 웹 / 백엔드 / 관리자 화면)
- 개발 일정, 담당 개발자

**작성 시 주의**
- 디자인 요청서가 있으면 요구사항 번호와 "확인할 것"을 이어받습니다.
- 기획서에 없지만 구현상 반드시 필요한 기능(예: 재입고 알림 "신청"만 있고 "발송"이 없는 경우)은 기능으로 적되 "원본에 명시 없음"으로 표시합니다.

**사용자용 예시 프롬프트**
```
[개발 요청서]
원본: (기획서 붙여넣기 또는 디자인 요청서)
플랫폼: 앱 + 백엔드
참고: 디자인 시안 (링크)
```

---

## 7. Jira 티켓 정리 (개발 요청서 변형)

**필수 입력**
- 개발 요청서 또는 원본 문서
- Jira 프로젝트 이름

**진행 순서**
1. 개발 요청서의 기능 하나를 티켓 하나로 나눕니다.
2. 티켓 목록(제목, 설명, 완료 기준)을 먼저 채팅에 보여 줍니다.
3. 사용자가 승인한 경우에만 Jira에 생성합니다. 승인 없이 만들지 않습니다.

---

## 8. 디자인·개발 요청서 함께 작성

**필수 입력**
- 원본 문서

**진행 순서**
1. 요구사항 번호를 한 번만 부여하고 두 문서에서 같이 씁니다.
2. 디자인 요청서를 먼저 쓰고, 그 "확인할 것"을 이어받아 개발 요청서를 씁니다. 개발 쪽에서만 생기는 질문은 번호를 이어서 추가합니다.
3. 채팅에는 두 문서 공통으로 가장 먼저 정해야 할 질문 3~4건을 보여 줍니다.
