# 디자인 요청서 점검표

요청서를 디자이너에게 넘기기 전에 점검합니다. 결과는 항목별로 `통과 / 보완 필요 / 해당 없음`으로 판정하고, 보완 필요 항목은 요청서 "확인할 것" 표에 질문으로 옮기거나 바로 수정합니다.

읽기 쉬움도 점검합니다: 본문에 REQ·SCR 번호가 섞여 있지 않은지, "한눈에 보기"만 읽어도 무엇을 몇 화면 그리는지 알 수 있는지 확인합니다.

디자인 단계 재작업은 대부분 상태 화면·예외 케이스·문구 누락에서 생깁니다. 그래서 2번과 3번을 가장 꼼꼼히 봅니다.

## 1. 원본 대조
- [ ] 원본의 모든 요구사항에 REQ ID가 있고, 매핑표에서 빠진 ID가 없다
- [ ] 각 REQ가 최소 하나의 SCR에 연결돼 있다 (연결 안 된 REQ는 "범위 밖" 또는 "미반영 사유"가 적혀 있다)
- [ ] 원본에 없는 정책·수치·문구를 확정된 것처럼 쓰지 않았다
- [ ] 원본 문서 제목·버전·링크가 상단에 적혀 있다

## 2. 화면 상태
- [ ] 화면마다 기본 / 로딩 / 빈 화면 / 에러 상태가 정의돼 있거나 "해당 없음" 사유가 있다
- [ ] 로그인 여부, 권한, 회원 등급 등 사용자 조건에 따라 달라지는 화면이 구분돼 있다
- [ ] 데이터 양 극단(0건, 1건, 매우 많음, 긴 텍스트)에서의 표시 방식이 정해져 있거나 확인 필요로 올라가 있다

## 3. 예외·정책
- [ ] 실패 케이스(네트워크 오류, 결제 실패, 재고 없음 등 도메인별)에 대한 화면 처리 방식이 있다
- [ ] 중복·동시 동작(버튼 연타, 이미 처리된 건 재시도)에 대한 처리 방식이 있거나 확인 필요로 올라가 있다
- [ ] 정책 항목마다 근거(REQ ID 또는 정책서)가 적혀 있다
- [ ] 법적 고지·약관·개인정보 관련 문구가 필요한 기능인지 확인했다

## 4. 흐름
- [ ] 각 화면의 진입 경로와 이탈(뒤로가기, 취소, 완료 후 이동) 경로가 있다
- [ ] 흐름 중 막다른 화면(다음 행동이 없는 화면)이 없다

## 5. 문구
- [ ] 확정 문구와 가안 문구가 구분돼 있다
- [ ] 같은 대상을 같은 용어로 부른다 (원본 용어 기준)
- [ ] 에러 문구에 사용자가 다음에 할 행동이 들어 있다

## 6. 전달 정보
- [ ] 플랫폼, 마감 희망일, 담당자가 적혀 있다 (모르면 확인 필요)
- [ ] 재사용할 컴포넌트·레퍼런스가 있으면 적혀 있다
- [ ] "이번에 하지 않는 것"이 채워져 있다 (없으면 "없음")
- [ ] 확인 필요 항목마다 확인 대상(PO·개발·법무 등)이 지정돼 있다

## 결과 표기 예시
| 영역 | 항목 | 판정 | 조치 |
|---|---|---|---|
| 화면 상태 | SCR-02 빈 화면 정의 | 보완 필요 | 쿠폰 0장일 때 표시 방식 → Q-03으로 등록 |
