# 개발 요청서 점검표

개발자에게 넘기기 전에 점검합니다. 항목별로 `통과 / 보완 필요 / 해당 없음`으로 판정하고, 보완 필요 항목은 "확인할 것"에 질문으로 옮기거나 바로 수정합니다.

개발 단계에서 일정이 밀리는 원인은 대부분 예외 처리 누락, 완료 기준 모호함, 개발 중에 정책이 정해지는 경우입니다. 그래서 2번과 3번을 가장 꼼꼼히 봅니다.

## 1. 원본 대조
- [ ] 원본의 모든 요구사항이 최소 하나의 기능에 연결돼 있다 (안 된 것은 "이번에 하지 않는 것" 또는 사유가 있다)
- [ ] 원본에 없는 정책·수치를 확정된 것처럼 쓰지 않았다
- [ ] 원본에 없지만 구현상 필요한 기능에는 "원본에 명시 없음" 표시가 있다
- [ ] 디자인 요청서가 있으면 요구사항 번호·용어·"확인할 것" 번호가 일치한다

## 2. 동작과 예외
- [ ] 기능마다 동작 규칙이 "조건 → 결과" 형태로 적혀 있다
- [ ] 로그인·권한·회원 상태에 따른 동작 차이가 정해져 있거나 확인할 것으로 올라가 있다
- [ ] 중복 요청(같은 동작 반복, 버튼 연타)에 대한 처리가 있다
- [ ] 대상이 사라지거나 바뀌는 경우(상품 삭제, 판매 종료, 옵션 변경) 처리가 있다
- [ ] 외부 연동 실패(알림 발송 실패, 결제 실패 등) 처리가 있다

## 3. 완료 기준
- [ ] 기능마다 완료 기준이 있다
- [ ] 완료 기준이 누가 봐도 통과·실패를 판단할 수 있는 문장이다
- [ ] 예외 처리도 완료 기준에 포함돼 있다

## 4. 비기능·데이터
- [ ] 개인정보를 다루는 기능이면 수집·보관·동의 관련 확인 항목이 있다
- [ ] 대량 처리(일괄 발송 등)가 있는 기능이면 규모나 제한 조건을 확인 항목으로 올렸다
- [ ] 성과 측정 지표와 남길 행동 로그가 적혀 있거나 확인 항목으로 올라가 있다

## 5. 범위와 전달
- [ ] 구현 방법(테이블·API·기술)을 요청서가 정하지 않았다
- [ ] "이번에 하지 않는 것"이 채워져 있다 (없으면 "없음")
- [ ] 확인할 것마다 확인 대상과 막히는 기능이 지정돼 있다
- [ ] "한눈에 보기"만 읽어도 몇 개 기능을 만드는지 알 수 있다
