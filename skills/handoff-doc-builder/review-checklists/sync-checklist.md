# 동기화 점검표

원본 변경을 디자인·개발 요청서에 반영한 뒤 점검합니다. 동기화에서 가장 흔한 사고는 "한쪽 문서만 고친 것", "바뀐 곳은 고쳤는데 연결된 다른 화면·기능을 놓친 것", "안 바뀐 곳까지 손댄 것"입니다.

## 1. 비교 정확성
- [ ] 수정된 원본의 모든 요구사항 번호에 대해 추가/변경/삭제/동일 판정이 있다
- [ ] 번호 없이 새로 생긴 요구사항에 신규 번호를 부여했고, 삭제된 번호를 재사용하지 않았다
- [ ] 단순 문장 다듬기(의미 변화 없음)를 "변경"으로 잘못 판정하지 않았다
- [ ] 반대로, 수치·조건·대상이 바뀐 경우를 "동일"로 놓치지 않았다

## 2. 영향 범위
- [ ] 변경된 요구사항에 연결된 모든 화면(디자인)과 기능(개발)을 찾았다 (관리 정보 표 기준)
- [ ] 디자인 요청서와 개발 요청서가 둘 다 있으면 양쪽 모두 반영했다
- [ ] 한 화면·기능의 변경이 앞뒤 흐름(진입 조건, 이동 경로, 연결 기능)에 주는 영향을 확인했다
- [ ] 정책 변경이 예외 처리, 오류 문구, 완료 기준에도 반영됐다
- [ ] 이미 시안이 나왔거나 개발이 진행된 부분에 영향이 있으면 "재작업 필요"로 표시했다

## 3. 문서 무결성
- [ ] 변경 없는 부분의 문장을 건드리지 않았다
- [ ] 삭제된 요구사항과 연결된 내용이 본문에 남아 있지 않다
- [ ] 문서마다 버전을 올렸고, 변경 이력에 날짜·변경 번호·내용·영향 범위를 적었다
- [ ] 두 문서의 요구사항 번호, 용어, "확인할 것" 번호가 서로 일치한다

## 4. 전달
- [ ] 디자이너용, 개발자용 변경 요약을 각각 작성했다 (재작업 필요 → 신규 → 삭제 → 확인할 것 순)
- [ ] 변경으로 새로 생긴 질문을 "확인할 것" 표에 추가했다
- [ ] "한눈에 보기"에 이번 변경 한 줄 요약을, 바뀐 화면·기능 제목에 버전 표시를 붙였다
