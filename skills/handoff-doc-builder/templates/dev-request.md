# 개발 요청서 양식

개발자가 "무엇을, 어떤 규칙으로, 어디까지 만들면 끝인지"를 한 번에 파악하게 하는 것이 목표입니다. 아래 원칙을 지킵니다.

- **구현 방법은 쓰지 않습니다.** 테이블 구조, API 이름, 기술 스택은 개발자가 정합니다. 요청서는 동작과 조건까지만 씁니다.
- **기능 제목 옆에만 요구사항 번호를 붙입니다.** 개발자가 티켓·기획서와 대조할 때 필요하기 때문입니다. 본문 문장에는 번호를 섞지 않습니다.
- **완료 기준은 확인 가능한 문장으로 씁니다.** "잘 동작한다" 대신 "같은 사용자가 같은 상품에 두 번 신청하면 두 번째 신청은 저장되지 않는다"처럼 씁니다.
- **정해지지 않은 것은 "확인할 것" 한 곳에 모읍니다.** 본문에는 "(확인할 것 3)"처럼 번호만 붙입니다.
- **디자인 요청서가 이미 있으면** 같은 요구사항 번호와 "확인할 것" 번호를 이어받습니다.

---

```markdown
# [기능명] – 개발 요청서

## 한눈에 보기
- **무엇을**: (기능을 한 문장으로)
- **왜**: (이유 한 문장)
- **구현할 기능**: N개 (1. 기능명 2. 기능명 …)
- **플랫폼**: 앱 / 웹 / 백엔드 / 관리자 (모르면 확인할 것으로)
- **일정**: (날짜, 모르면 확인할 것으로)
- **관련 디자인**: (디자인 요청서·시안 링크, 없으면 "없음")
- **아직 정해지지 않은 것**: N건 → 맨 아래 "확인할 것" 참고

---

## 기능 1. [기능명] (REQ-01)

**사용자 관점 동작**
(누가, 언제, 무엇을 하면, 시스템이 어떻게 반응하는지 한두 문장)

**동작 규칙**
- (조건 → 결과 형태로. 예: 품절 상품에만 버튼을 노출한다)

**필요한 데이터**
- (저장하거나 불러와야 하는 정보. 이름만, 구조는 쓰지 않음)

**예외 처리**
- (실패, 중복, 대상 삭제, 권한 없음 등 정상 흐름이 아닐 때)

**완료 기준**
- [ ] (확인 가능한 문장)

---

## 기능 2. [기능명] (REQ-02)
(같은 구조 반복)

---

## 비기능 요구사항
- 성능, 보안·개인정보, 발송량, 로그 보관 등 기획서에 있는 조건만. 없으면 "기획서에 없음"으로 적고 필요하면 확인할 것으로 올림

## 데이터 수집 (성과 측정)
- 측정할 지표와 남겨야 할 행동 로그 (예: 버튼 노출, 클릭, 신청 완료). 기획서에 없으면 확인할 것으로

## 이번에 하지 않는 것
- (범위 밖 항목, 없으면 "없음")

## 확인할 것
| 번호 | 질문 | 누구에게 | 막히는 기능 |
|---|---|---|---|
| 1 | | PO / 개발 / 법무 | 기능 1 |

---

| 요구사항 | 내용 | 개발 기능 | 디자인 화면 |
|---|---|---|---|
| REQ-01 | | 기능 1 | ① |

|---|---|---|---|
| v1.0 | YYYY-MM-DD | 최초 작성 (원본: 기획서 제목·버전) | - |
```

## 작성 메모
- 하나의 요구사항이 여러 기능으로 나뉘면 기능마다 같은 번호를 붙입니다 (예: 신청 저장과 알림 발송이 모두 REQ-01에서 나온 경우 → 기능 1·2 모두 REQ-01). 기획서에 없는데 구현상 꼭 필요한 기능(예: 재입고 시 알림 발송)은 "원본에 명시 없음"을 표시하고 확인할 것으로 올립니다.
- "확인할 것"의 "막히는 기능" 열은 개발 착수 순서를 정하는 데 씁니다. 막히는 게 없는 기능부터 먼저 시작할 수 있습니다.
- Jira 티켓으로 바꿀 때는 기능 하나를 티켓 하나로 보고, 제목은 "[기능명]", 설명은 동작 규칙·예외 처리, 완료 기준은 그대로 옮깁니다.
